Реалізація одного зрізу TechDesk

Специфікація ЛР1 у docs/ - єдине джерело правил. Не змінюй її, щоб спростити патч.
Шляхи docs/, app/, tests/ вказано від кореня репозиторію; references/ - від теки цього Skill.

Розподіл відповідальності (docs/architecture.md)
- app/schemas.py - перевірка вхідних і вихідних даних (Pydantic);
- app/services.py - бізнес-правила, переходи статусів, фільтрація;
- app/database.py - збереження в SQLite, параметризовані запити;
- app/routes.py / app/main.py - HTTP-маршрути та мапінг помилок.

Процедура
1. Визнач зріз (A-D) за запитом. Якщо запит охоплює кілька зрізів, запропонуй почати з одного.
2. Знайди зріз у references/slices.md і прочитай лише зазначені там розділи docs/.
3. Перелічи перевірки: критерії приймання та сценарії T01-T14, яких стосується зміна.
4. Надай план із 3-5 пунктів і дочекайся підтвердження.
5. Внеси мінімальну зміну лише в дозволених для зрізу файлах разом із тестами.
6. Перевір diff: якщо є робота з файлами поза tmp_path, мережа, запуск процесів або видалення даних - зупинись.
7. Запусти перевірки з кореня репозиторію:
   python -m pytest -q
   python -m ruff check app tests --select E4,E7,E9,F,I
   Після двох невдалих спроб виправлення зупинись і опиши причину людині.
8. Надай фактичний підсумок перевірок і окремо зазнач, що потребує рішення людини.

Заборони
- Не змінюй маршрути, поля й коди відповідей із docs/api-contract.md.
- Не додавай і не оновлюй залежності; не змінюй конфігурацію середовища.
- Запускай лише команди перевірки з кроку 7.
- Не послаблюй і не видаляй наявні тести, щоб вони пройшли.
- Не додавай функцій поза обсягом ЛР1 (реєстрація, видалення тікетів, пагінація, Docker, FR-08).
- SQL - лише параметризовані запити; тести - лише на тимчасовій базі (tmp_path).
- Рішення прийняти зміну завжди за людиною.

Формат відповіді
Зріз -> прочитані розділи docs/ -> перевірки -> план -> diff -> підсумок pytest і ruff -> що не зроблено.
