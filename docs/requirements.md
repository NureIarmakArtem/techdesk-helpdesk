1. Вихідний запит та межі проєкту

Запит замовника:
Невеликій IT-команді потрібна система для обліку звернень користувачів щодо технічних проблем. Співробітник створює тікет із назвою й описом. Фахівці підтримки переглядають тікети, призначають виконавця, визначають пріоритет, змінюють статус і додають коментарі. Потрібно швидко бачити важливі відкриті тікети. У майбутньому система має допомагати автоматично визначати категорію та пріоритет звернення.

Стек: Python, FastAPI, SQLite, pytest. Демонстрація через REST API та Swagger UI.

Функціональні вимоги:
| Код | Можливість | Межа реалізації |
|-----|------------|-----------------|
| FR-01 | Створення тікета | Назва й опис; статус OPEN; пріоритет medium за замовчуванням; виконавець null. |
| FR-02 | Перегляд та фільтрація | Список і один тікет за ID; фільтри status і priority окремо та разом (логічне AND). |
| FR-03 | Редагування тікета | Часткове оновлення (PATCH) полів title, description, priority, assignee_id. Статус змінюється окремо. |
| FR-04 | Керування статусом | Лише дозволені переходи за матрицею станів; помилки не змінюють дані. |
| FR-05 | Призначення виконавця | Вибір із двох тестових користувачів (1 або 2); null знімає призначення. |
| FR-06 | Коментарі | Додавання та перегляд коментарів до наявного тікета від відомого автора (1 або 2). |
| FR-07 | Збереження й валідація | SQLite; збереження після перезапуску; некоректні запити відхиляються. |
| FR-08 | Рекомендація AI | Категорія, пріоритет і короткий підсумок; не змінює тікет автоматично. |

Поза обсягом (Out-of-Scope):
Реєстрація, паролі, OAuth, рольова авторизація, email-сповіщення, вкладення, видалення тікетів, повнотекстовий пошук, пагінація, складний frontend, Docker, хмарне розгортання, векторна БД. Два користувачі - лише тестовий довідник без автентифікації.

3. Аналіз неоднозначностей і журнал рішень

3.1. Власний аналіз до звернення до AI:
1. Хто такі користувачі та як вони створюються? - Закрито замовником: два фіксовані користувачі (1 - Agent A, 2 - Agent B), без API створення та автентифікації.
2. Які статуси й переходи дозволені? - Закрито замовником: OPEN, IN_PROGRESS, CLOSED; без повернення назад; дозволено OPEN -> CLOSED.
3. Обмеження довжини та обов'язковість опису? - Закрито замовником: title 3..120 після trim; description 0..2000 (може бути порожнім); коментар 1..1000.
4. Допустимі пріоритети? - Закрито замовником: low, medium, high (регістр важливий), типове medium.
5. Операції із закритим тікетом? - Закрито замовником: редагування й зміна статусу заборонені; перегляд і коментарі дозволені.
6. Порядок сортування списків? - Закрито замовником: у порядку створення.
7. Прогалина: поведінка при переході CLOSED -> CLOSED та при порожньому тілі {} у PATCH. - Вирішено в п. 3.2 і розд. 5.

3.2. Рішення після критичного діалогу з AI:
| № | Пропозиція AI | Класифікація | Рішення |
|---|---------------|--------------|---------|
| 1 | Розділити помилки на 404 (не знайдено), 409 (конфлікт стану), 422 (валідація). | Корисне уточнення форми | Прийнято. Однозначний HTTP-код для кожного типу помилки. |
| 2 | Повертати 409 для переходу CLOSED -> CLOSED. | Припущення, що потребує перевірки | Відхилено. За правилом замовника повторне встановлення поточного статусу не є помилкою (200 OK без змін). 409 лише при зміні статусу. |
| 3 | Заборонити невідомі поля та порожнє тіло {} у PATCH (код 422). | Корисне уточнення форми | Прийнято. Запобігає одруківкам клієнта і порожнім запитам. |
| 4 | Застосовувати strip() до title і body коментаря перед перевіркою довжини. | Заданий факт (title) + уточнення (body) | Прийнято. Виключає коментарі з одних пробілів. |

4. User Stories та критерії приймання

US-01 (FR-01, FR-07): Як співробітник, я хочу створити тікет із назвою й описом, щоб зафіксувати технічну проблему.
- AC-01-01 (позитивний): Given запит із title "  Не працює принтер  " без description, priority, assignee_id, When тікет створюється, Then API повертає 201, title стає "Не працює принтер", description "", status "OPEN", priority "medium", assignee_id null, генеруються id і created_at (UTC), дані зберігаються після перезапуску.
- AC-01-02 (негативний): Given title "  ab  " (довжина 2 після trim) або priority "HIGH", When надсилається запит, Then API повертає 422 і запис не створюється.

US-02 (FR-02): Як інженер підтримки, я хочу переглядати список тікетів із фільтрами та відкривати один тікет, щоб швидко знаходити важливі відкриті звернення.
- AC-02-01 (позитивний): Given тікети (OPEN, high), (OPEN, low), (CLOSED, high), When запит GET /tickets?status=OPEN&priority=high, Then API повертає 200 і лише (OPEN, high) у порядку створення.
- AC-02-02 (граничний): Given немає тікетів IN_PROGRESS, When запит GET /tickets?status=IN_PROGRESS, Then API повертає 200 і [].
- AC-02-03 (негативний): Given тікета id=999 не існує, When запит GET /tickets/999, Then API повертає 404.

US-03 (FR-03, FR-07): Як інженер підтримки, я хочу частково редагувати тікет, щоб оновлювати окремі поля без зміни решти.
- AC-03-01 (позитивний): Given відкритий тікет із priority "low", When PATCH містить лише {"priority": "high"}, Then API повертає 200, змінюється тільки priority.
- AC-03-02 (негативний, атомарність): Given відкритий тікет, When PATCH містить валідний priority "high" і невалідний title "a", Then API повертає 422 і жодне поле в БД не змінюється.
- AC-03-03 (негативний): Given тікет CLOSED, When PATCH змінює title, Then API повертає 409 і дані не змінюються.

US-04 (FR-04): Як інженер підтримки, я хочу змінювати статус тікета окремою операцією, щоб відображати хід роботи за регламентом.
- AC-04-01 (позитивний): Given тікет OPEN, When зміна статусу на IN_PROGRESS або CLOSED, Then API повертає 200 з новим статусом.
- AC-04-02 (негативний): Given тікет CLOSED, When зміна статусу на OPEN, Then API повертає 409 і статус лишається CLOSED.
- AC-04-03 (граничний): Given тікет IN_PROGRESS, When зміна статусу на IN_PROGRESS, Then API повертає 200 без змін.

US-05 (FR-05): Як тімлід, я хочу призначати виконавця або знімати призначення, щоб розподіляти задачі.
- AC-05-01 (позитивний): Given відкритий тікет з assignee_id null, When PATCH {"assignee_id": 2}, Then 200 і assignee_id = 2; при PATCH {"assignee_id": null} повертається 200 і assignee_id = null.
- AC-05-02 (негативний): Given відкритий тікет, When PATCH {"assignee_id": 3}, Then API повертає 422 і виконавець не змінюється.

US-06 (FR-06, FR-07): Як інженер підтримки, я хочу додавати й переглядати коментарі до тікета, щоб фіксувати діагностику навіть після закриття.
- AC-06-01 (позитивний): Given наявний тікет (включно з CLOSED), When додається коментар з author_id 1 і непорожнім body, Then 201, а GET коментарів повертає їх у порядку створення.
- AC-06-02 (негативний): Given наявний тікет, When body "   " або author_id 99, Then API повертає 422 і коментар не зберігається.
- AC-06-03 (негативний): Given тікета id=999 не існує, When POST або GET коментарів, Then API повертає 404.

US-07 (FR-05, FR-07): Як клієнт API, я хочу отримувати список користувачів і перевіряти стан сервісу, щоб коректно формувати запити.
- AC-07-01 (позитивний): Given запущений сервіс, When GET /users, Then 200 і [{"id": 1, "name": "Agent A"}, {"id": 2, "name": "Agent B"}].
- AC-07-02 (позитивний): Given запущений сервіс, When GET /health, Then 200 і {"status": "ok"}.
- AC-07-03 (негативний): Given запущений сервіс, When POST /users, Then 405 Method Not Allowed, список користувачів не змінюється.

US-08 (FR-08): Як інженер підтримки, я хочу отримувати AI-рекомендацію категорії, пріоритету й підсумку, щоб швидше сортувати тікети без автозміни даних.
- AC-08-01 (позитивний): Given наявний тікет, When запит AI-рекомендації, Then 200 з suggested_category, suggested_priority, summary; тікет у БД не змінюється.
- AC-08-02 (негативний): Given LLM недоступна, When запит AI-рекомендації, Then 503, а FR-01..FR-07 працюють без змін.

5.2. Матриця переходів статусів (3x3)

| Поточний \ Цільовий | OPEN | IN_PROGRESS | CLOSED |
|---------------------|------|-------------|--------|
| OPEN | Без змін (успіх) | Дозволено | Дозволено |
| IN_PROGRESS | Заборонено | Без змін (успіх) | Дозволено |
| CLOSED | Заборонено | Заборонено | Без змін (успіх) |

Операції для статусу CLOSED:
- Перегляд тікета: дозволено.
- Додавання і перегляд коментарів: дозволено.
- Редагування основних полів (title, description, priority, assignee_id): заборонено.
- Зміна статусу на OPEN або IN_PROGRESS: заборонено. Повторне CLOSED: без змін (успіх).

5.3. Правила часткового оновлення (PATCH)

Реалізується через розрізнення відсутнього ключа (model_fields_set у Pydantic v2) та null, із забороною зайвих полів (extra="forbid").
1. Поле не передано - залишається старе значення.
2. Передано assignee_id: null - призначення виконавця знімається.
3. Передано null для title, description або priority - помилка валідації, дані не змінюються.
4. Передано порожнє тіло {} - помилка валідації.
5. Передано невідоме або заборонене поле (id, created_at, status тощо) - помилка валідації.
6. Змішаний запит (коректне + некоректне поле) - атомарна відмова: жодна зміна не зберігається.

5.4. Каталог результатів і помилок

- Успішне створення: збереження в SQLite, повернення об'єкта з id і created_at.
- Успішне читання/зміна: повернення актуального об'єкта або списку.
- Немає збігів за фільтром: успішний результат, порожній список [].
- Тікета не існує: відхилення (ресурс не знайдено), дані не змінюються.
- Некоректні вхідні дані: відхилення (помилка валідації), дані не змінюються.
- Суперечність стану (редагування CLOSED, заборонений перехід): відхилення (конфлікт стану), дані не змінюються.

5.5. Зв'язки та впорядкування

- Зовнішні ключі SQLite (PRAGMA foreign_keys = ON): Ticket.assignee_id -> User.id; Comment.ticket_id -> Ticket.id; Comment.author_id -> User.id.
- Списки тікетів і коментарів завжди впорядковані за часом створення: ORDER BY created_at ASC, id ASC.
